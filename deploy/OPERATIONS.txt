MAINTENANCE — EXISTING INSTANCE
- Use deploy/RECOVERY.md and scripts/deploy-server-safe.mjs for all planned
  server updates/rollbacks. The guard requires a drained, empty single machine
  and an immutable reviewed image. Do not bypass it with direct fly deploy.
- SIGUSR2 to the Node process enters drain mode: new upgrades and create/join
  commands are rejected; existing matches continue. /readyz becomes 503;
  /healthz stays 200 to keep the instance and existing sockets alive.
- Wait until /healthz reports zero connections and zero rooms before updating.
  This can require players to return to menus/leave, and completed-room retention
  may take 15 minutes. Do not assume a deploy can preserve ongoing matches.
- SIGTERM shuts down, with a bounded five-second socket cleanup deadline.
- Draining is one-way until restart. If deployment is canceled, wait for rooms
  to finish, then restart the same release to reopen admission.
- Initial launch uses one instance. A crash/restart loses active rooms; there is
  no automatic resume. Do not advertise seamless rolling upgrades or HA.

MONITORING
- /healthz and /readyz: non-cacheable JSON with content version and aggregate counts.
- Production emits one JSON health log per minute: rooms, connections, RSS and
  event-loop p95 delay. No player IPs, room codes or credentials are logged.
- Provider alerts: restarts, memory pressure, CPU saturation, event-loop delay,
  failed health checks, outbound traffic and spend. Thresholds require hosted data.

- Ordinary log events are capped at 120/minute per process; a later event reports

HIGH-PRIORITY ISSUES
H1 — Rebinding from pause abandons the current match UI. FIXED.
Where: apps/client/src/main.ts, bind action (~959–983), refreshBindings (~587).
Reproduction: enter a match, pause, open Settings, choose a keyboard binding,
then press a valid key (even its existing key). The old implementation navigated
to full-screen Settings and removed the pause UI; there was no resume route.
Root cause: the capture callback called settings() with its default overlay=false,
which invoked navigate('settings') and replaced the entire screen.
Fix: refresh only the binding labels in the existing view. Update both sides of
swapped bindings; clear pending input; preserve the match and pause state.
Verified: reproduced in the browser before the fix; after the fix both pause and
settings dialogs remained open, Back returned to pause, Resume returned to the
same match, and movement/reset worked. Automated handler test also checks swaps
and that a later key cannot trigger a second commit.
Regression risk: low. Binding assignment rules and game simulation are unchanged.

H2 — Connection-loss recovery is hidden behind native modal menus. FIXED.
Where: main.ts disconnectMessage (~782), pause (~811),
toggleOnlineControllerMenu (~126), controllerBack (~134).
Reproduction: open online Options (or nested Settings), then lose the connection.
The old MATCH INTERRUPTED div existed in the DOM, but the open modal dialog
kept it inert and out of the accessible UI. The old Return to fight control also
remained available despite the failed connection.
Root cause: terminal connection handling appended a normal overlay without
closing/replacing native top-layer dialogs or invalidating menu input state.
Fix: cancel binding/controller capture, clear menu/input state, replace the old
UI with the existing interruption panel, focus Main Menu, and prevent pause/
online-menu controls from reopening the failed match. Controller Back exits to
Main Menu. Loading revision invalidation remains in place.
Verified: isolated local WebSocket fixture triggered a real browser connection
close before and after the fix. Before: only the old online dialog was accessible.
After: nested Settings disappeared, recovery was focused and clickable, Escape
could not resume combat, and Main Menu worked. Automated tests cover duplicate
notifications, capture cancellation and pause/back handling.
Regression risk: low to moderate, limited to terminal client UI transitions.
Normal network messages, rollback and disconnect/forfeit simulation are unchanged.

MEDIUM ISSUES
M1 — Settings can leave a keyboard capture listener active after closing. FIXED.
Where: main.ts closeSettings (~582), controllerBack (~134), settings cancel
handler (~600), settings-close action (~911), openControllers (~114).
Reproduction: while paused, click a binding so it says PRESS KEY, then click
Settings Back before entering a key. Previously the window capture listener
survived removal of its dialog. The next gameplay key could change the binding,
consume that input, and previously also navigate away via H1.
Root cause: close paths removed the dialog without calling cancelBinding.
Fix: route Settings close/cancel through one small close helper that cancels
capture, clears input and resets menu navigation. Opening Controllers also
cancels an in-progress keyboard rebind.
Verified: automated Back-button/controller-back cancellation tests; browser
pending-capture -> Back -> key -> Resume sequence. No unintended binding change
or navigation occurred; movement worked after resuming.
Regression risk: low; only cancellation/close handling changes.

LOW ISSUES
No additional low-priority defect was confirmed within this focused pass.
Unrelated formatting, duplication and visual cleanup were left alone.

FIXES IMPLEMENTED
- Preserve the current match while committing a settings key binding.
- Refresh swapped binding labels without replacing the screen.
- Remove pending key capture when leaving its settings context.
- Clear obsolete dialogs/capture on terminal disconnect and expose recovery.
- Keep failed matches input-locked until the user leaves.
No combat or character behavior was changed.

AREAS THAT STILL LOOK TECHNICALLY RISKY
These are review/coverage risks, not newly confirmed bugs or reasons to redesign
working systems during this audit:
- main.ts coordinates many global flags, async callbacks and nested dialogs.
  Further overlay entry/exit paths should use the same capture cleanup discipline.
- Successful shared sprite/texture caches intentionally live for the application
  lifetime. The finite current roster bounds them, but a longer soak is needed
  to distinguish intended caching from GPU/resource growth.
- Loading catches rejected resources and guards stale revisions, but several
  image/fetch requests rely on browser/network timeouts rather than a single
  application loading deadline. Test requests that stall without rejecting.
- The frame loop and client message callback assume valid internal state and
  compatible server payloads. Unexpected renderer failures or malformed server
  data can still require stronger diagnostics/recovery; no speculative broad
  exception-swallowing or protocol rewrite was introduced.
- Character-specific behavior remains distributed across systems. Adding fighters
  requires interruption/KO/reset tests for every new optional state field.

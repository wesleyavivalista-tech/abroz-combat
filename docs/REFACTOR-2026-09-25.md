# Incremental architecture refactor — 25 September 2026

## Completed

- Shared damage application and extracted normal hit/block resolution.
- Generic returning projectiles, periodic contact attacks, timed action deadlines and configurable mode finales; removed fighter-name and special move-name dispatch from shared combat/simulation.
- Shared actor ordering, target profiles, swept projectile geometry and debug geometry.
- Optional state-entry restrictions, definition validation, animation contract/atlas validation and reusable attachment alignment.
- Separate Roms presentation loader as the migration example; existing artwork/renderers retained.
- Typed observational gameplay events, suppressed during rollback replay, and expanded scrollable F1 diagnostics.
- Client/server content compatibility enforced at room creation/join; protocol 35.
- Architecture and character/ability creation guides rewritten to match implementation.

## Evidence

- Pre-refactor checkpoints cover all 87 existing moves, each across 1,801 ticks with movement and hitstop. The same state hashes still match after normalizing four renamed snapshot keys.
- Full typecheck, lint and 242 tests pass. Production client/server build passes.
- Regression coverage includes a differently named fighter using the same abilities, registration of 20 extra definitions, six simultaneous modes, cleanup/replay, invalid definitions, damage stacking and actual network rejection of an outdated client.
- Browser check loaded Roms versus Gut training, enabled F1 diagnostics, and fired the hose. The dummy was pushed to the arena boundary and the journal recorded continuous damage.
- No artwork generation or balance changes were included. Existing authored atlas pivot metadata remains supported.

## Deliberate boundaries

This preserves the working state machine and the specialized mechanic modules. It does not replace every renderer with a single animation engine, introduce a speculative ECS, or claim to validate anatomy with automated tests. Existing presentation adapters can migrate to manifests as their art is updated. Unique future mechanics still require a tested reusable implementation; ordinary attacks and the extracted ability types do not require new engine branches.
